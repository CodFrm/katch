# 最近请求落库与逐请求日志降级

> Status: Draft
> Owner: katch
> Last updated: 2026-09-14

**Objective:** 让「最近请求」这块面板读数不再依赖日志文件的有界尾部——历史落进数据库、
保留期由界面设置，同时把逐请求的拉取日志从 info 降到 debug，把这条写入从默认开启的
热路径上摘下来。

**Hard invariant:** 记录这份历史不得让拉取变慢、变贵或失败。库写不进去、缓冲区满了、
保留期配得很小，都只能是「面板少几条」，不得影响任何一次拉取的响应、状态码与耗时。

## Problem

1. **逐请求的拉取行站在拉取热路径上，而它唯一的消费者只是一块诊断面板。**
   每一次拉取都会走 `logger.Ctx(ctx).Info`（`internal/metrics/metrics.go` 的 `logPull`），
   经 zap 的 `TeeCore` 同步写到两个 core：lumberjack 文件（`AddSync`，每次一行一次
   `os.File.Write`，全程持锁）与 stdout（`configs/config.yaml` 的 `disableConsole: false`）。
   所有请求 goroutine 串在同一把锁上——这是这台机器吞吐的第一个瓶颈，
   而 `docs/observability.md` 给这行日志定 info 的唯一理由是「最近请求面板读它」。
2. **「最近请求」能看见的窗口由日志文件大小决定，不由时间决定。**
   `log_svc` 只读文件末尾 256 KiB（`defaultTailBytes`，约 1300 行），而 lumberjack 的
   轮转阈值是 `MaxSize: 2MB`。流量越大，这个窗口覆盖的时间越短：1000 req/s 时约 1.3 秒，
   多个上游分流时单个上游在这些行里凑不满默认的 30 条，`limit=100` 更是不可能。
   面板要回答的是「刚刚发生了什么」，而它能回答的区间随流量缩水。
3. **面板的可见性被日志配置绑死。** `logger.logFile.enable: false`（日志全在 stdout 上，
   被容器运行时收走）时 `log_svc` 直接返回空，这块面板永久消失；文件刚被轮转走的那一瞬
   同理。落盘与否是部署形态的选择，不该决定一块管理面板存不存在。

## Actors and user stories

1. 作为**运维者**，我希望在上游详情里回看某个上游最近若干次拉取，并且这个能力与流量大小、
   日志是否落盘无关，这样「刚刚发生了什么」不会随着站点变忙而变得看不见。
2. 作为**运维者**，我希望在磁盘吃紧时把这份历史的保留期自己改小、立即生效，这样
   「这台机器扛不住这么多历史」由我决定，而不是由代码里一个写死的数决定。
3. 作为**运维者**，我希望默认配置下的日志文件里不再有逐请求的拉取行，这样磁盘与写带宽
   不被排障用的明细常年占用；需要它时把日志级别临时调到 debug 就能拿回来。

## Design decisions

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | 逐请求的拉取行从 **info 降到 debug** | 它唯一的消费者是「最近请求」面板，面板改读库之后这行没有消费者。debug 默认关闭，于是默认配置下这次写入整个消失（zap 在 level 检查处返回）。字段一个不少地保留——排障时把级别调到 debug 仍能拿回同一行。否决：保留 info——继续为一块已被替代的面板把明细写进每一台部署的磁盘 |
| 2 | 面板的历史落一张新表，**不是日志** | 见「数据模型」。落库让「能看见什么」由时间与保留期决定，与日志文件大小、轮转、是否落盘全部解耦 |
| 3 | 保留期是**纯时间**维度（默认 24 小时），不设每上游行数上限 | 用户决定：磁盘扛不住就自己把保留期改小。代价（磁盘占用随流量线性增长）写在「已知代价」一节，不假装它不存在。否决：每上游行数上限——面板一屏 30 条、上限 100 条，行数上限会把「能回看多久」变成一个随流量浮动的数，而用户要的是一个能自己设的时间 |
| 4 | 落库是**每秒一批**的批量写，热路径只做一次内存 append | 每请求一个写事务会和缓存元数据抢 sqlite 的唯一写者，这正是决策 16 点名否决的形态；而批量写让热路径的成本与现在攒分钟桶完全同量级。1 秒是这个成本下能换到的最小滞后，面板的滞后上限即 1 秒。否决：每请求同步写库——把热路径拖进事务；否决：跟 rollup 一样 60 秒落一次——「刚刚发生了什么」会变成「一分钟前发生了什么」 |
| 5 | 待落库的缓冲区有**硬行数上限**（2 万行），满了丢最旧 | 这是防「库变慢 → 内存涨」的那道闸，和保留期不是一回事：保留期管库里留多久，缓冲上限管内存最多占多少。1 秒的窗口里这个上限只有库卡住时才可能被摸到 |
| 6 | 保留期是 setting 表里的一项，键 `recent_request_retention_seconds` | 它属于「进程跑起来之后才生效、应该能在界面上改」的一侧（决策 4 的边界）。单位取秒：仓库里所有时长项都是秒，前端现成的时长输入与 `formatDuration` 直接复用，写 `24h` 就行。否决：单位取小时——为一项设置多开一套单位约定 |
| 7 | 不新增「开关」项 | 没有被要求的能力。一个关不掉记录的开关在没有需求时会退化成多一处要维护的分支 |
| 8 | 未知主机（不在上游表内）仍然不记 | 和指标、日志现在一致：拉取路径公开，让任何人往磁盘上写字符串是一条不需要密码的放大路径；这类请求也没有 `upstream_id` 可挂 |
| 9 | 落库失败丢弃这一批并记 error，且**不得按秒刷日志** | 库短暂不可用是可接受的事件，面板少几秒的量不影响任何人；但一个不可用的库不该顺带把日志刷爆。保留重试会引入一个需要自己设上限的队列，收益只是一秒的行 |
| 10 | 启动时先裁一次，再进入每小时的裁剪循环 | 把保留期改小之后，重启成为一个立刻见效的止血手段，而不必再等最多一小时 |
| 11 | 面板的读取路径由日志文件改为这张表 | 接口的请求与响应结构**保持不变**（`admin.RecentRequests*`），面板组件与取数钩子零改动 |

前一份 spec（`2026-09-12-multi-upstream-mirror-proxy`）里被本轮取代的两处说法：
「最近请求（读结构化日志的有界尾部，不另建每请求的表）」与决策 16 注解中
「否决：每请求写库」对本面板的适用性——本轮的否决理由只对**热路径上的写**成立，
而第 4 条决策的热路径不写库。

## 数据模型

`recent_request`
: `upstream_id`、`at`（这次拉取**结束**的时刻，秒）、`object`（上游内的路径，registry 的
  不含 `/v2` 前缀）、`result`（`hit` / `miss` / `denied` / `origin_error`，与
  `katch_requests_total` 同一套取值）、`bytes`（发给客户端的字节数）、`duration_ms`、
  时间戳。索引：`(upstream_id, at)` 供面板按上游取最近若干条，`at` 单独一个供保留期裁剪。
  表名按仓库既有约定由实体名单数化、再带上 `db.prefix`（与 `traffic_rollup` →
  `katch_traffic_rollup` 同形），所以库里是 `katch_recent_request`。

它和 `traffic_rollup` 不是同一种东西：那张表答「这段时间总共怎么样」（可加，每分钟一行，
留 90 天），这张答「刚刚按什么顺序发生了什么」（不可加，每请求一行，留由设置决定的时长）。
合成一张表会让两者互相迁就，而它们要回答的问题不同。

迁移只向 `migrationList()` 末尾追加，不修改既有迁移。

## 记录与落库

一次拉取结束后（与计数同一个缝，`internal/metrics` 的中间件），这条记录被 append 进
进程内的环形缓冲。热路径在这里付出的代价是一次内存写入，不查库、不写库、不等待。

一个后台循环每秒把缓冲区取走（取走即清空）并批量插入；启动时先按当下的保留期裁一次，
之后每小时裁一次 `at` 早于「此刻减去保留期」的行。

落库时主机名要翻成 `upstream_id`（表按 id 存，面板也按 id 查）。期间上游被删掉的行没有
归属，丢弃即可。

## 面板

上游详情的「最近请求」按 `upstream_id` 取最近若干条，最近的在前，同一秒内的多条按写入
顺序倒序，顺序是确定的。返回条数上限仍是 100 条（`admin.RecentRequestsMaxLimit`），
服务层再夹一道，响应大小不由调用方决定。

- 与流量无关：窗口由保留期和条数上限决定，不随站点变忙而缩水；
- 与日志配置无关：日志没开落盘时面板照常工作；
- 停用的上游：已经落库的历史行仍然可见（面板按 `upstream_id` 查，不受上游启停影响），
  这样「我停用它正是因为它在出问题」这件事之后还能回看现场。停用那一刻尚未落库的
  最多 1 秒的量没有归属，会缺。
- 库里没有这个上游的行（新装的站、或该上游确实没被拉过）时给空列表，面板照现有约定
  整块不渲染。

## 设置

设置界面新增一项「最近请求保留时长」，默认 `24h`，可写 `1h` / `12h` / `3d` 这样的形式，
取值范围 3600 秒 ~ 604800 秒（7 天）；解不出来的输入沿用现有的「拦住保存」处理，超出范围由
后端按既有数值项的方式拒绝。提示文案要说明它是这份历史占用磁盘的唯一闸门——**保留期越长，
库越大，且与流量线性相关**。

改小保留期后最多一小时真正释放（裁剪每小时一次），重启会立刻裁一次。

## 失败与降级

- **库写不进去**（锁等待超时、库不可用）：丢掉这一批并记一条 error，不重试；连续失败时
  这条错误按分钟节流，不按秒刷日志。缓冲区已满时继续丢最旧，内存不涨。
- **进程退出**：退出前落一次，最多丢 1 秒的尾部。
- **库读不出来**：面板照现有约定整块消失，不报错、不阻塞整屏管理界面。
- **保留期配得极小**：面板只给得出更少的行，这是配置的选择而不是故障。

## 已知代价

- **磁盘占用随流量线性增长，没有硬上界**。100 req/s ≈ 1.5 GB/24h，1000 req/s ≈ 15 GB/24h
  （行宽约 150–200 B）。这取代了现在「日志总量封在 `2MB × 10` 备份」的性质——从常数变成
  线性，是这项改动唯一不可撤销的部分。
- **sqlite 删行不缩文件**：空间靠空闲页复用，峰值定终身。保留期是事后止血，不是事前限流。
- **面板滞后最多 1 秒**（批量落库的间隔）。
- **默认配置下日志里不再有逐请求的拉取行**：排障时要先把日志级别调到 debug 才能 grep。

## Out of scope

- **面板的筛选、翻页、按对象搜索**：本轮只把存储换掉，多出来的能力下一轮再谈；
- **把这份历史开放给公开页面**：它是运营数据，仍在管理接口后面；
- **按对象或按结果的聚合**：那由 `traffic_rollup` 与回源原因四列回答；
- **把 `traffic_rollup` 也改成可配置保留期**：90 天是那张表的口径，本轮不动；
- **多副本共享**：这张表和 `traffic_rollup` 一样按单实例写入。

无法自动化的部分：**高流量下的磁盘增速与每小时裁剪的耗时**。它需要一次本地的运行时观察
——生成一段持续流量，记录库文件大小、每小时裁剪的日志与面板滞后，只跑一次真实进程能给出
结论。这部分靠运行时观察覆盖，不进单测。
