# 多上游镜像代理

> Status: Draft
> Owner: katch
> Last updated: 2026-09-12

**Objective:** 让使用者把任意受支持上游的 URL 前缀换成 katch 的域名，就能通过 katch
拉取该资源，并在重复拉取时命中本地缓存；让运维者在界面上完成上游、访问规则与缓存的
全部管理，不必登机器改文件。

**Hard invariant:** katch 不得成为开放代理——只有上游表里启用的主机可被访问；
响应体在任何情况下都不被改写（APT 与 Go proxy 的内容带签名/校验和，改一个字节就失效）。

## Problem

1. **受限网络下，容器镜像、系统软件包、Go 模块、GitHub 资源的拉取各自需要一套加速方案。**
   现状是每类上游配一个专用镜像（registry mirror、APT 源、GOPROXY、raw 代理），
   四套配置、四个域名、四种故障模式，新机器初始化要重复一遍。
2. **重复拉取浪费回源带宽。** 同一个基础镜像层、同一个 deb 包、同一个模块版本会被
   反复从上游下载；这些对象绝大多数是内容寻址的，本可以只取一次。
3. **改一个上游要改文件、重启进程。** 加一个镜像源、暂停一个出问题的上游、封一个有
   CVE 的镜像，都是运维日常动作，不该每次都经过「登机器 → 编辑 YAML → 重启」。

## Actors and user stories

1. 作为**使用者**，我希望在首页输入 `redis:7` 这样的一句话，直接拿到可执行的拉取命令，
   这样我不必先理解路径规则，也不必翻文档。
2. 作为**使用者**，我希望把 `https://` 换成 `https://katch.example.com/` 就能拉取资源，
   这样我不必为每类上游记一套不同的配置写法。
3. 作为**运维者**，我希望在界面上增删改上游、暂停出问题的上游，改完立刻生效，
   这样上游变更不再是一次发布。
4. 作为**运维者**，我希望能声明「哪些镜像/路径允许被代理」，并且在保存前就能验证
   某个具体地址会被哪条规则决定，这样规则不是一张要在脑子里模拟的正则表。
5. 作为**运维者**，我希望看到每个上游的命中率、回源量和缓存占用，并能搜索、清理
   单个缓存对象，这样我不必登到机器上删目录。
6. 作为**运维者**，我希望缓存占用有上限并自动回收，这样磁盘不会被悄悄撑满。

## Design decisions

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | 路径第一段是上游主机名 | 使用者只需记一条规则；加新上游是加一条记录而非新的路径约定。否决：按类型分区（`/apt/`、`/registry/`）——类型划分不完备，GitHub 一家就同时是 raw、release 两种资源 |
| 2 | 保留段与上游段靠**点号**区分：第一段含 `.` 即上游主机名 | 公网主机名必然含点，规则不会随上游增加而退化。否决：维护一张保留字表——每加一个自身端点都要同步改表 |
| 3 | **上游是数据库记录，不是配置文件条目**；`config.yaml` 只留基础设施配置 | 增删上游、暂停上游是运维日常动作，做成配置项意味着每次变更都要改文件并重启。否决：配置文件 + 热重载——既要处理「正在回源的请求引用了已被删除的上游」，又要解决配置文件与界面两个写入源的冲突，复杂度高于直接落库 |
| 4 | `config.yaml` 的边界是「**进程起不来就没法从界面改的东西**」：监听地址、数据库 DSN、日志、缓存目录、初始管理密钥 | 这是一条可判定的规则，而不是逐项拍脑袋。数据库连不上时界面本身就不可用，所以 DSN 必须在文件里；配额、TTL、并发这些进程跑起来之后才生效的参数，一律落库 |
| 5 | registry 的 token 由 katch 自己换取，不透传给客户端 | 受限网络下客户端直连 `auth.docker.io` 本就不通，透传等于整个代理白做。否决：透传 `WWW-Authenticate` 的 realm——实现简单但在目标场景下不可用 |
| 6 | 上游表即白名单，不在表内或已停用的主机返回 404 | 任意主机名转发等于开放代理，会被当作匿名跳板和 SSRF 入口。否决：黑名单——永远列不全 |
| 7 | 缓存按对象是否**内容寻址**分两档：不可变对象长期缓存 + LRU 淘汰；可变对象短 TTL | digest/版本号寻址的对象内容永不改写，可安全长期持有；tag、`InRelease`、`@latest` 会变，缓存久了会发出过期内容 |
| 8 | 缓存写入必须原子（先写临时文件再改名） | 进程在下载中途退出时，半个文件若被当成完整缓存，之后每次命中都返回损坏内容，且不会自愈 |
| 9 | 同一对象的并发回源合并为一次 | 冷启动时大量客户端同时拉同一个基础镜像层，不合并会把并发原样放大到上游 |
| 10 | 拉取路径公开，`/api/v1/admin` 需密钥 | 镜像站的价值在于任何人可直接用；而清缓存、改规则是破坏性操作 |
| 11 | 不把客户端的 `Authorization` 转发给上游 | 首版只代理公开资源，转发客户端凭据会把它泄漏给上游，且无实际用途 |
| 12 | 协议类别只有 `static` 与 `registry` 两种，其余差异优先靠上游记录的字段表达 | container registry 的鉴权与标准端点保留语义属于协议行为；其他 HTTP 上游的差别主要是「哪些路径不可变」，这是数据而非代码。否决：每个具体上游一个硬编码适配器——加一个 APT 镜像就要改一次代码、发一次版 |
| 13 | 标准 registry 端点按协议判定可变性，其余路径由每条上游记录的模式列表补充 | registry blob 与 digest manifest 内容寻址，tag manifest、referrers 与 tags 列表会变化，不能被宽泛模式覆盖；APT 的 `pool/`、Go proxy 的 `@v/`、raw 的 40 位 commit SHA 等路径仍用模式列表表达。否决：在代码里按 host 分支判断——等价于把具体上游配置写死进二进制 |
| 14 | 访问规则分**全局**与**上游内**两层，全局先于上游内求值 | 「禁止一切 `:latest`」这类策略跨上游成立，逐个上游重复配置必然漏配 |
| 15 | 同层内规则按**具体度**排序，不按人工顺序；首个匹配者决定结果 | 拖拽排序的列表里，插入一条新规则就可能悄悄改变另一条的结果，而这个副作用在界面上不可见。具体度定序是确定性的，且与人的直觉一致（`library/alpine:3.21` 比 `library/*` 更该说了算）。代价是「为什么是这条命中」不再显然——用界面上的规则测试器补偿，见「管理界面」 |
| 16 | 界面上的命中率、请求量、规则命中数来自**进程内计数器 + 分钟级 rollup 表**，不依赖外部 Prometheus | 一个自部署的镜像站不该为了看自己的命中率就要求先搭一套监控。`/metrics` 仍然是标准的 Prometheus 端点供外部采集，rollup 表只是同一批计数器的定时快照。否决：管理后端反查 Prometheus——把可选组件变成硬依赖；否决：每请求写库——把热路径拖进事务 |
| 17 | 上游连续回源失败时进入**退避**（内存态，不落库），界面标为「限流中/降级」 | 上游限流时继续全量打过去只会延长封禁；退避状态是运行时事实，重启后重新探测即可，落库反而会把过期状态带到下一个进程 |
| 18 | 管理密钥以哈希存库，`config.yaml` 里的是**初始密钥**，仅在库中尚无密钥时生效 | 首次启动必须有办法登进去，而之后的轮换应该在界面上完成、不必改文件。否决：密钥长期只存在于 `config.yaml`——与「运行时配置在界面上改」的边界冲突 |

## 数据模型

`upstream`
: `host`（唯一）、`kind`（`registry` / `static`）、`origin`（回源地址）、`enabled`、
  `immutable_patterns`（路径模式列表）、`mutable_ttl_seconds`、`note`、时间戳。

`access_rule`
: `upstream_id`（可空，空即全局规则）、`action`（`allow` / `deny`）、`pattern`、
  `note`、时间戳。上游的默认策略（`allow_all` / `deny_unless_matched`）是 `upstream`
  上的一个字段，不是一条规则——它没有 pattern，混进规则表只会让具体度排序无从谈起。

`setting`
: 键值表（值为 JSON）。站点域名与名称、首页是否公开上游列表、缓存配额与回收水位、
  可变对象默认 TTL、回源并发上限、上游超时与重试、管理密钥哈希。

`traffic_rollup`
: `upstream_id`、`bucket`（整分钟）、`requests`、`hits`、`denied`、`origin_errors`、
  `bytes_served`、`bytes_origin`，以及四个回源原因计数：`miss_first`（首次拉取）、
  `miss_ttl`（TTL 过期）、`miss_evicted`（缓存被淘汰）、`miss_changed`（上游 digest 变更）。
  每分钟由进程内计数器落一行，保留 90 天。
  界面的 24 小时 / 7 天 / 30 天区间与回源原因分解都从这张表聚合。

  回源原因做成这张表上的四列而不是一张每请求的明细表，是因为界面只需要占比，
  而占比是可加的；决策 16 否掉每请求写库的理由在这里同样成立。

`cache_object`
: `upstream_id`、`key`（上游内路径或 digest）、`digest`、`size`、`immutable`、
  `pinned`、`expires_at`、`last_access_at`、`hit_count`。LRU 淘汰与界面上的对象搜索
  都走这张表；文件本体在磁盘上按内容寻址存放，同一份内容只存一份。

迁移只向 `migrationList()` 末尾追加，不修改既有迁移。

## 路径分发

请求进入后按以下顺序判定，第一条命中即止：

- `/api/...`、`/metrics` 是 katch 自身的端点；
- `/v2/...` 是 container registry 协议。客户端固定请求这个前缀，**上游主机名在它之后**
  （`/v2/docker.io/library/redis/manifests/7`）。对 `/v2/` 本身的探测请求返回 200；
- 第一段含 `.` 的，该段即上游主机名，其后是原样的上游路径；
- 其余路径交给前端 SPA。

上游不存在、已停用、或被访问规则拒绝时，一律返回 404 / 403，且响应不包含该主机名——
避免把 katch 变成探测内网主机是否存在的工具。上游表在进程内有缓存，管理接口写入后
主动失效，读路径不为每个请求查库。

## 上游行为

**Container registry**（docker.io、ghcr.io、quay.io）

拉取 `katch.example.com/docker.io/library/redis:7` 时，客户端会向 katch 请求
`/v2/docker.io/library/redis/manifests/7`。katch 向上游发起同样的请求，收到 401 与
`WWW-Authenticate` 后自行换取 token 并重试，对客户端始终表现为一个不需要鉴权的 registry。
token 按（上游、仓库、scope）缓存到过期前，不为每个请求重新换取。

Docker Hub 的官方镜像需要补全命名空间：使用者写 `docker.io/redis` 时，向上游请求的是
`library/redis`。这个补全只对 docker.io 生效，由上游记录上的一个标志控制。

manifest 按 digest 请求时不可变；按 tag 请求时短 TTL。blob 一律按 digest 寻址，长期缓存。

**APT**（deb.debian.org、archive.ubuntu.com 等）

原样转发。`pool/` 下的 `.deb` 按路径长期缓存；`InRelease`、`Release`、`Packages*`
短 TTL。响应体不得改写——它们在 `InRelease` 的 GPG 签名覆盖范围内。

**Go module proxy**（proxy.golang.org）

`@v/*.zip`、`*.info`、`*.mod` 按模块版本寻址，长期缓存；`@v/list` 与 `@latest` 短 TTL。
`/sumdb/` 子路径必须一并代理——它是 GOPROXY 协议的一部分，缺了它校验会失败。

**GitHub 静态资源**（raw.githubusercontent.com、github.com 的 release 资产）

raw 路径按 commit SHA 请求时不可变，按分支名请求时短 TTL。release 资产会被上游
302 重定向到另一个主机，katch 跟随该重定向并把最终内容返回给客户端，不把重定向
本身透给客户端——否则客户端会直连一个不在上游表内、且在受限网络下不可达的地址。

## 访问规则

规则回答一个问题：**这个资源允许被代理吗**。求值顺序：

1. 全局规则按具体度排序，首个匹配者决定；
2. 未被全局规则决定时，该上游的规则按具体度排序，首个匹配者决定；
3. 仍未被决定时，落到该上游的默认策略（`allow_all` 或 `deny_unless_matched`）。

具体度的定序规则：字面前缀长者优先，前缀等长时通配符少者优先，仍相等时 `deny` 优先。
这条规则必须是纯函数并直接被测试覆盖——它决定了每一次拒绝是否正当。

被拒绝的请求返回 403，计入 `denied`，并且**不回源、不写缓存**。

## 缓存

缓存命中时直接返回本地副本；未命中时一边向客户端流式转发，一边写入缓存——
不得先下载完整对象再开始响应，那会让大文件的首字节时间等于整个下载时间。

缓存总容量有上限（运行时设置），超过回收水位时按最近最少使用淘汰。淘汰只发生在
不可变且未被 pin 的对象上；可变对象由 TTL 自行过期。

已缓存对象在读取时校验完整性（有 digest 的按 digest 校验，无 digest 的按记录的大小
校验）；校验失败时丢弃该副本并回源，同时记一条 error——这类失败意味着磁盘或写入路径
出了问题，不能静默自愈了事。

## 扩展点

上游是一条记录：主机名、协议类别、回源地址、不可变路径模式列表。标准 registry
端点的保留语义由协议类别给出，其余 HTTP 路径由模式列表补充。由此得到两条可验证的边界：

**只加一条记录就能支持的**：任何「HTTP GET + 内容寻址」形态的新上游。再加一个 APT
镜像、一个新的 container registry、一个 npm 或 PyPI 源，都属于此类——katch 不需要改
代码、不需要重启进程，在界面上添加一条上游即可。这一条要由测试守住：用例通过
**管理接口**注册一个此前不存在的假上游，在不修改任何生产代码、不重启进程的前提下
完成拉取与缓存命中。

**必须写或扩展适配器的**：需要 GET 之外的协议语义，或标准端点本身带有缓存语义的
上游。git 的 `git-upload-pack` 是 chunked POST 且响应不可缓存；registry 需要 token 交换、
路径重写，并要求 blob/digest manifest 永久缓存而 tag/referrers 保持可变——这类差异是
行为而非数据，记录字段表达不了。新增协议类别时只有确有协议语义的层需要随之扩展，
管理接口与具体上游配置不应按 host 增加分支。

这条边界是刻意划的：把静态与非标准路径的「哪些路径不可变」做成数据，是因为它每个
上游都不同但形状相同；把 token 交换和标准端点语义留在代码里，是因为它们由协议统一
定义且形状不同。强行让后者可配置，只会得到一个表达能力不足、又比代码更难懂的配置格式。

## 失败与降级

- 上游不可达或超时：返回 502，**不缓存**该响应；
- 上游返回 4xx：原样透传状态码，不缓存；
- 上游连续失败达阈值：进入指数退避，期间快速失败并在界面标为「降级」，
  退避是内存态，进程重启后重新探测；
- 缓存目录不可写或磁盘写满：降级为纯透传并记 error，服务继续可用——
  缓存是优化，它坏掉不该让拉取整体失败。**已知缺口**：写入失败发生在下载中途时，
  当前实现会中断这次响应而不是转为透传，因为那个临时文件同时是合并回源的扇出缓冲；
  补上它需要重做缓冲层，见 Out of scope；
- 数据库不可用：读路径用进程内的上游/规则/设置缓存继续服务，管理接口返回 503——
  拉取不该因为管理面的存储故障而中断；
- 回源过程中客户端断开：已下载部分仍写完缓存（值得，下一个请求就能命中），
  除非上游连接同时失败。

## 可观测性

`/metrics` 暴露（除 `component.Core()` 已注册的 Go runtime / process 指标外）：

- `katch_requests_total{upstream,kind,result}`，`result` ∈ `hit` / `miss` / `denied` / `origin_error`
- `katch_request_duration_seconds{upstream,kind}`（直方图）
- `katch_bytes_served_total{upstream,source}`，`source` ∈ `cache` / `origin`
- `katch_origin_requests_total{upstream,status}` 与 `katch_origin_duration_seconds{upstream}`
- `katch_origin_inflight{upstream}`、`katch_origin_backoff{upstream}`
- `katch_cache_objects{upstream}`、`katch_cache_bytes{upstream}`
- `katch_cache_evictions_total{reason}`，`reason` ∈ `lru` / `ttl` / `manual`
- `katch_cache_integrity_failures_total{upstream}`
- `katch_rule_decisions_total{scope,decision}`
- `katch_token_exchanges_total{upstream,result}`

不导出命中率这类比值——它由 `hit / (hit + miss)` 推导，导出成 gauge 只会在采样窗口
不一致时给出两个互相矛盾的数字。界面上的命中率同样是推导值。

日志与追踪的约定见 [docs/observability.md](../observability.md#logging)。

## 管理接口与界面

`/api/v1/admin/*` 需要密钥。密钥错误返回 401，且不区分「密钥错误」与「未提供密钥」。
接口覆盖：上游的增删改查与启停、访问规则的增删改查、规则试算（给一个资源地址，
返回判定与匹配过程）、缓存对象的搜索/清除/pin、设置的读写与密钥轮换、
概览与单上游的聚合指标读取。

界面分两个面，设计稿在 `~/Code/设计稿/katch.pen`：

**前台**（公开）

- **拉取助手**：整页由一个输入框驱动。输入 `redis:7` 或任意资源地址，
  实时给出识别结果（属于哪个上游、哪类资源）和可复制的拉取命令，外加一条
  「写进 daemon 配置长期生效」的入口。不做分类命令卡——使用者不该先理解规则才能用。
  侧栏是命中率、缓存量、节省的回源流量和近 14 天趋势；页脚是支持的上游表，
  「支不支持我要的东西」不用点进去就能答。是否公开上游列表与命中率由设置控制。

**后台**（需密钥）

- **概览**：全局指标条 + 12 个上游的健康矩阵（命中率、近 12 小时请求量、状态）
  + 事件流。自动告警与人为变更放在同一条时间线上，带操作人。
- **上游**：主从布局。左栏常驻上游列表，右侧是选中上游的全部信息——指标条、
  24 小时命中/回源堆叠图、回源原因分解、最近请求（读结构化日志的有界尾部，
  不另建每请求的表）。运维的问题几乎都是
  「某个上游怎么了」，平级模块会逼人跳页拼信息。
- **访问规则**（上游下的一个 tab）：左侧是默认策略开关与按具体度排序的规则表，
  右侧是**规则测试器**——粘一个资源地址，直接给判定、命中第几条、以及完整的匹配
  过程。这是决策 15 的配套：具体度定序换来了确定性，代价是「为什么是这条命中」
  不再显然，测试器把这个代价还回去。
- **缓存对象**：顶部是按上游分段的容量条，下面是搜索 + 筛选 + 批量操作的对象表。
- **设置**：只放运行时项，顶部明写「监听地址、数据库、日志在 `configs/config.yaml`
  里，改动需要重启」——两类配置的边界画在界面上，而不是留给用户猜。
- **登录**：密钥表单，并说明管理接口默认只监听回环地址。

界面遵循一条排版规则：**机器产出或消费的一律等宽**（主机名、镜像引用、路径、字节数、
命中率、时间戳），**人写的一律无衬线**（标题、按钮、说明）。深浅两套主题共用同一套
变量。文案中英双语，默认中文；**不复述命令自己会打印的输出**，也不放「正在加载」这类
解释性横幅——状态用控件自身的形态表达。后端返回的英文错误串不直接贴给用户。

## Out of scope

- **git clone 代理**（`git-upload-pack` 的 chunked POST、不可缓存语义与这一轮完全不同）——下一轮；
- **私有仓库**：只代理公开资源，不转发客户端凭据；
- **多用户与角色**：只有一把管理密钥，没有账号体系；
- **按用户的配额与限流**：首版靠上游表和部署侧限流；
- **多副本共享缓存**：首版是单进程本地磁盘缓存，`traffic_rollup` 也按单实例写入；
- **规则的审批流与版本回滚**：变更记进事件流，但不做草稿与回滚；
- **下载中途写满磁盘时转为透传**：开头就写不进去（目录不可写）已经能正确降级，
  但中途失败要先把扇出缓冲与落盘拆开，是一次独立的缓冲层改造，不塞进本轮；
- **链路追踪**：见 docs/observability.md 的说明。

## Testing decisions

| 缝 | 验证什么 | 现有依据 |
|---|---|---|
| 路径分发（纯函数） | 保留段与上游段的判定、`/v2/` 的上游位置、上游不存在/停用时 404 且不回显主机名 | 无 |
| 规则求值（纯函数） | 具体度定序、全局先于上游内、默认策略兜底、`deny` 在平局时优先 | 无 |
| 上游/规则 repository | SQL 拼写与约束（host 唯一、删除上游级联其规则） | sqlmock，不用真库 |
| 上游适配器（httptest 假上游） | registry 的 401→换 token→重试、docker.io 的 `library/` 补全、release 的 302 跟随、`/sumdb/` 被代理 | 无 |
| 缓存层 | 原子写（中断不留半个文件）、LRU 淘汰、TTL 过期、并发回源只回一次、校验失败时回源、pin 的对象不被淘汰 | 无 |
| 流式转发 | 大对象的首字节不等待整体下载完成；客户端断开时缓存仍写完 | 无 |
| 退避 | 连续失败进入退避、期间快速失败、恢复后退出退避 | 无 |
| rollup | 分钟桶写入、区间聚合、保留期裁剪 | 无 |
| 管理接口 | 无密钥/错密钥均 401 且不可区分；上游 CRUD、规则 CRUD、规则试算、清缓存按上游生效 | 无 |
| 前端 | 拉取助手的识别与命令生成、规则测试器的展示、密钥无效时的提示 | `frontend/tests/App.test.tsx` |
| 扩展点 | **经管理接口**注册一个新的假上游后，不改生产代码、不重启进程即可完成拉取与缓存命中 | 无 |
| `make smoke` | 扩展：启动后经管理接口加一个假上游，完成一次完整的拉取—缓存—命中 | `scripts/smoke.sh` |

无法自动化的部分：与真实上游（docker.io、deb.debian.org、proxy.golang.org、GitHub）
的连通性和协议兼容性。这部分靠一次人工的运行时验证覆盖——用真实 `docker pull`、
`apt-get update`、`go mod download` 各跑一遍并记录结果。
