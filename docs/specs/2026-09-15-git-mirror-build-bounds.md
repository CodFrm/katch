# git 建镜像的三道闸：体积、停滞与总时限

> Status: Approved
> Owner: katch
> Last updated: 2026-09-15

**Objective:** 让一次 git 建镜像在越过体积上限、上游停止送字节或整体耗时过长时被立即中止、
现场清理干净、名额归还，并在 `last_error` 上说明是哪一道闸拦的；使公开拉取路径上的任何客户端
都无法通过 clone 一个大仓库让 katch 无界地占用磁盘、内存与建镜像名额。

**Hard invariant:** 建镜像中止后盘上不得留下半个裸仓库——它会被计入配额且永远不会自愈；
建镜像名额必须归还。既有的白名单与只读性质不受本 spec 影响。

## Problem

1. **单仓上限只约束保留，不约束下载（运行时实测）。** 检查发生在克隆**完成之后**：把
   `git_repo_max_bytes` 设为 5MB 后拉 `octocat/Hello-World`，盘上先长到 27MB（5.2 倍）才转
   `rejected`，错误信息为「仓库体积超过单仓上限：21355074 字节 > 5242880 字节」——量的是已经
   下载完的仓库。
2. **无时间闸，一次建镜像可以无限期占着名额。** 同一次验证里，对 `octocat/Spoon-Knife` 用默认
   1GB 上限观察到：盘上冲到 1840MB（1.8 倍于上限），进程 RSS 2.1GB，状态在约 19 分钟里一直
   `pending`，其间盘上体积完全不增长而 CPU 持续 89%——下载已经结束，卡住的是 go-git 的 delta
   解析阶段。该次观察由人主动终止，否则不会自行结束。
3. **拉取路径按设计是公开的**（首版 spec 决策 10），因此上面两条的触发条件只是「任何人 clone 一个
   大仓库」，不需要任何凭据。
4. **既有的超时确实套在建镜像上，但 go-git 在解析阶段不认它。** `git_sync_timeout_seconds`
   已经包住初次建镜像（含排队），见 `internal/service/git_svc/mirror.go:262-264`；实测那 19 分钟
   没有被它中止，是因为 go-git 的 delta 解析阶段整个不看 context——
   `remote.go:590` 的 `packfile.UpdateObjectStorage` 一路到
   `plumbing/format/packfile/common.go:26` 都没有 ctx 参数。**因此任何基于 context 取消的闸，
   在这一段上都是失效的**；能中止它的只有让它正在读的 reader 或正在写的 storer 报错。

   进一步查明：解析阶段**读**得到、**写**不到。
   `storage/filesystem/dotgit/writers.go:55` 在建 `PackWriter` 时就起了解析 goroutine，
   它与下载**并发**运行，通过 `:41` 的 `fs.Open` 读那个临时 pack；而 `:62` 的
   `packfile.NewParser(s, w.writer)` 只传 idx writer，storage 为 nil（`parser.go:99`），
   所以整个解析期间**没有任何字节落盘**，idx 在内存里建，盘上再长要等 `PackWriter.Close`。
   两条推论：其一，体积闸不可能「等到解析阶段才新越界」——体积是写入时单调累加的，超标必然
   落在下载途中那一次写上；其二，能掐断解析的是**读侧**报错，因此闸必须在 Read 与 Write
   两侧都报错并且一旦触发就粘住。
5. **go-git 的调用点只有一处，且没有现成的注入缝。** `internal/service/git_svc/builder.go:45`
   的 `git.PlainCloneContext`；`CloneOptions` 没有 transport 字段，传输层由一个进程级全局
   注册表解析（`plumbing/transport/client/client.go:16-32`）。按 build 注入只能走
   `git.CloneContext(storer, worktree, opts)` 配一个自带计量的 storer，而不是改全局状态。

## Actors and user stories

1. 作为**运维者**，我希望一个超标仓库在下载途中就被拦下，这样磁盘不会先被占满再被清理。
2. 作为**运维者**，我希望一次打不通或磨死的建镜像能自己结束并归还名额，这样一个坏仓库不会把
   建镜像能力长期占住。
3. 作为**运维者**，我希望从 `last_error` 一眼看出这次是「太大」「上游不送了」还是「整体太久」，
   这样我知道该调哪一项设置还是该换上游。

## Design decisions

| # | 决策 | 依据与被否方案 |
|---|---|---|
| 1 | 体积在**接收字节处**累计，越界立即中止 | 周期性量目录会留下一个与下载速率成正比的超出量；在字节处计数没有这个窗口。否决：维持下载后再量——正是 Problem 1 的成因 |
| 1b | 三道闸的**判据**一律是那个会在越界时报错的 reader/storer，不是 context 取消；取消只保留一处，且只用来**叫醒**一次停在网络读上的下载（见下） | Problem 4：解析阶段不看 ctx，基于 ctx 的闸在那一段上形同虚设，而实测卡死正发生在那里。闸在 Read 与 Write 两侧都报错、一旦触发即粘住；读侧是掐断解析的唯一入口。三道闸共用同一个机制，也就只有一处需要证明「它在解析阶段仍然有效」 |
| 2 | 新增**停滞闸**，只在 fetch 阶段计时：上游连接在该时长内未送来任何新字节即中止 | 与回源客户端的既有先例同向——`internal/proxy/origin/origin.go` 刻意不设总时限，理由是「一个几百 MB 的镜像层会稳定地在读到一半时被它掐断」，改用只跑到响应头的计时器。否决：把「盘不长且无字节」一律当停滞——实测的解析阶段正是网络静默而 CPU 满载，那样会误杀一次合法的解析 |
| 3 | 新增**总时限闸**，覆盖从开始拉到镜像可用的整段墙钟；建镜像路径改由它管，`git_sync_timeout_seconds` 退回只管增量同步 | 停滞闸按定义管不到解析阶段，而实测卡死正发生在那里。体积闸负责拦大仓库，所以这个值可以设得宽松。否决：两者叠加——出厂值下 600 秒总是先到，新设置永远不会生效，站长必须同时调大两个才能建一个大仓库 |
| 4 | 三道闸分成**三项独立设置**，不合并 | 三者量的是三件不同的事，合用一个值会逼站长为了容纳一个大仓库而把停滞容忍度一起放大 |
| 5 | 超体积转 `rejected`，超停滞与超总时限转 `failed` | 沿用既有语义：`rejected` 是「这个仓库本身不适合镜像」，永久穿透；`failed` 是「这次没成」，与上游抖动同类 |
| 6 | `last_error` 必须写明是哪一道闸 | 三种中止外观相同的话，站长看到 `failed` 无从判断是上游慢、上游死还是仓库太大 |
| 7 | 中止时目录清理干净、名额归还 | 半个裸仓库会被计入配额且永不自愈；实测那 19 分钟 `pending` 全程占着一个并发名额，是次生故障 |
| 8 | **不收敛 refspec**，镜像照旧与上游逐 ref 一致 | 用户决定。明示后果见「非目标」 |

### 决策 1b 的一处细化：取消用来叫醒，不用来判断

**纯 reader/storer 的停滞闸单独立不住**。上游安静下来的时候，
下载那一侧停在传输层的 `Read` 里（`io.Copy` 从连接读往 `PackWriter` 写），
与它并发的解析 goroutine 停在 `syncedReader.sleep` 的 `<-s.news` 上
（`storage/filesystem/dotgit/writers.go:265`）——两处都不经过文件系统这道缝。
此时把闸合上没有任何人看得见：没有写，就不会有下一次 `Write`；没有写，
解析那一侧也永远等不到 `news`。建镜像会就这么挂着，正是本 spec 要消灭的那个现象。

因此保留一处取消：`cloneBounded` 自己建一个 `context.WithCancel`，闸合上之后调它，
唯一的作用是让那一次停在网络读上的 `Read` 报错返回。它**不是判据**：

- 是哪一道闸、错误怎么分类，都由闸自己说了算（`cloneBounded` 优先报 `bounds.err()`）；
- 解析阶段的中止仍旧只靠读侧报错，那一段整个不看 ctx；
- 建镜像拿到的 ctx 上**没有** deadline（`git_sync_timeout_seconds` 不再挂在这里），
  取消只可能由闸触发。

回归防线：`TestBounds_TimeGatesCloseTheSameSeam` 用一个什么都不做的叫醒函数驱动两道
时间闸，把「合闸与解析阶段的中止都不依赖取消」钉死；`TestCloneBounded_ParseDiesOnItsNextRead`
钉的是解析确实死在读侧。

「中止时的可观察结果」一节不受这处细化影响：三道闸的状态、`last_error`、目录清理与
名额归还都照旧。

## 数据与设置

不新增表。`git_mirror` 的状态集合与既有一致（`pending` / `ready` / `failed` / `rejected`）。

设置面新增两项运行时项，与既有 git 设置同组，落 `setting` 表而非配置文件（首版 spec 决策 4）：

- **建镜像停滞时限**，默认 120 秒。计时口径：fetch 阶段内，距上一次从上游收到字节的时长。
- **建镜像总时限**，默认 1800 秒。计时口径：从开始建镜像到镜像可用为止的墙钟时间。

`git_repo_max_bytes` 保持原名与原默认值（1GiB），只有生效时机从「下载完再量」变成「收到即累计」。

`git_sync_timeout_seconds` 保持原名与原默认值（600 秒），但**生效范围收窄**：它不再覆盖初次建镜像，
只管增量同步。升级的可观察后果是建镜像的时限由出厂的 600 秒变成新设置的 1800 秒；这是有意的，
两者量的本就是不同的事（决策 3、4）。

## 中止时的可观察结果

三道闸中任意一道触发时：建镜像立即停止；该仓库的镜像目录被清理干净，盘上不留残余；
建镜像的并发名额立刻归还，下一个待建仓库可以马上开始；镜像记录落到对应状态并在 `last_error`
上写明触发的是哪一道闸；相应的状态变化进事件流，与既有镜像事件同一套出口。

体积闸触发时，盘上峰值不超过上限加上一次 pack 写入缓冲的量级——不再出现实测里那种数倍于上限
的占用。

客户端一侧不受影响：这三种中止都发生在后台建镜像上，当次拉取照旧由穿透完成并成功。

## Out of scope

- **收敛镜像的 refspec。** 用户决定照旧全拉 `+refs/*:refs/*`。明示后果：GitHub 会在默认广播里
  暴露 `refs/pull/*`，实测 `octocat/Spoon-Knife` 有 62931 条 ref、其中 62927 条是 `refs/pull/*`，
  `octocat/Hello-World` 有 3596 条。这类仓库会稳定撞上体积上限并永久走穿透，本地加速实际只对
  PR ref 不多的仓库生效。
- **约束 go-git 的堆内存。** Go 无法直接限制堆；实测 RSS 2.1GB 只能由体积闸间接收敛。
- **`failed` 之后的重试策略。** 维持现状，不在本 spec 内。
- **`/metrics` 泄漏白名单成员**（本 spec 之前就存在）与**镜像目录双 `.git` 后缀**。
  两者都留档，各自另开 spec。
- **配额淘汰的节拍。** 实测在 10 分钟一拍时正常工作，不在本 spec 内。

## Testing decisions

| Seam | 验证什么 | 现有同类 |
|---|---|---|
| 假上游 + 建镜像（service 层） | 喂超过上限的字节流：盘上峰值不超上限、状态 `rejected`、目录清空、`last_error` 指明体积闸 | `internal/service/git_svc/builder_test.go` 已有进程内假上游（`client.InstallProtocol`），不需要 git 二进制 |
| 同上 | **闸能掐断正在跑的解析**：体积闸在下载途中触发后，与下载并发的解析 goroutine 因下一次读报错而立刻结束，建镜像随即返回并清场，而不是等解析跑完。这一条是 Problem 4 的直接回归防线——只认 ctx 的实现会在这里留红 | 无现成同类 |
| 同上 | 送一段字节后挂起不再送：在停滞时限内被中止、状态 `failed`、`last_error` 指明停滞闸 | 同上 |
| 同上 | 以极慢但持续的速率送：停滞闸不误伤，总时限到点中止、`last_error` 指明总时限闸 | 同上 |
| 同上 | 一次正常的 clone 走完之后停滞闸已经收工：再久的静默也不算停滞。守的是决策 2 的「不误伤解析」——收工点挂在 `storer.PackfileWriter` 那个 writer 的 `Close` 上，这一层被摘掉的话停滞闸会一路计进解析阶段 | 无现成同类 |
| 同上 | 三种中止各跑一次后，下一个建镜像能立刻开始（名额已归还） | `internal/service/git_svc/sweep_test.go` 的租约用例 |
| 设置（service + 前端） | 两项新设置可读写、即时生效、越界值被拒 | `internal/service/setting_svc/setting_test.go`、前端设置页用例 |

三道闸都用**可控的假上游**驱动，不碰公网：公网仓库的体积与速率都不在用例的掌控内，拿它做判据
会让用例的成败取决于当天的网络。运行时验证那一侧已经用真实公网证过问题存在。
